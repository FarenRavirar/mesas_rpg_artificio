# BUG-004 — `persistMessages` envia arrays JS para coluna JSONB e quebra todo INSERT

**Reportado:** 2026-05-09
**Identificado durante:** execução de T-EXEC-1 (spec 016).
**Severidade:** crítica — bloqueia toda reingestão; ingest pré-existente operava por sorte com payloads "compatíveis".
**Status:** Patched localmente, pendente de deploy.
**Branch alvo:** `feat/015-discord-draft-pipeline`

---

## Sintoma

Ao chamar `POST /admin/discord-sync/sources/:id/reingest-force` (sem janela de tempo), backend retorna `{"error":"Erro ao buscar mensagens."}` (HTTP 500) e logs mostram:

```
[POST /admin/discord-sync/fetch] error: invalid input syntax for type json
    at /app/node_modules/pg/lib/client.js:631:17
    at process.processTicksAndRejections (node:internal/process/task_queues:104:5)
    at async PostgresConnection.executeQuery (/app/node_modules/kysely/dist/cjs/dialect/postgres/postgres-driver.js:93:49)
    ...
    at async InsertQueryBuilder.execute (/app/node_modules/kysely/dist/cjs/query-builder/insert-query-builder.js:1108:24)
    at async persistMessages (/app/dist/discord/ingestMessages.js:195:9)
    at async ingestForumMessages (/app/dist/discord/ingestMessages.js:280:24)
    at async /app/dist/routes/adminDiscordSync.js:619:15
```

Como `reingest-force` faz `DELETE FROM discord_import_messages WHERE status NOT IN ('synced')` **antes** de chamar `ingestForumMessages`, e o INSERT subsequente quebra, a tabela fica **vazia** sem dado novo persistido.

## Reprodução

Pré-requisitos: ambiente Beta após migration 117, com Message Content Intent ON, com fonte de fórum cadastrada.

1. Snapshot pré:
   ```sql
   SELECT count(*) FROM discord_import_messages WHERE source_id='<source>';
   -- Ex.: 103
   ```
2. `POST /admin/discord-sync/sources/<source>/reingest-force` body `{}`.
3. Snapshot pós:
   ```sql
   SELECT count(*) FROM discord_import_messages WHERE source_id='<source>';
   -- Ex.: 0
   ```

Reprodução observada em 09/05/2026 com perda local de:
- `📖┃campanhas`: 103 → 0 (incluindo 10 com body recuperado em 06/05)
- `🎯┃one-shots`: 77 → 0
- Drafts derivados: 169 → 0

Mesas publicadas (`tables.status='active'`) **não** afetadas.

## Causa raiz

Kysely com `PostgresDialect` padrão delega serialização de parâmetros ao driver `node-postgres` (`pg`). O driver:

- **Para objetos JS comuns** (`{...}`): chama `JSON.stringify` automaticamente. Funciona para coluna JSONB.
- **Para arrays JS** (`[...]`): converte em **literal de array Postgres** (`'{a,b,c}'`), que NÃO é JSON válido.

`backend/src/discord/ingestMessages.ts` em `persistMessages` ([linhas 243, 244, 252, 266, 267 do código atual](../../../backend/src/discord/ingestMessages.ts#L243)) passa `msg.embeds` e `msg.attachments` (arrays) diretamente:

```ts
attachments: (msg.attachments ?? []) as unknown[],
embeds: (msg.embeds ?? []) as unknown[],
```

Como Discord Forum starters frequentemente trazem `attachments` ou `embeds` não-vazios, o array literal Postgres é gerado e Postgres recusa: `invalid input syntax for type json`.

### Por que não foi detectado antes?

- 11/180 mensagens persistidas anteriormente tinham `embeds` como **array** (`jsonb_typeof='array'`) — provavelmente inseridas via path/script diferente (manual ou versão anterior do código).
- 169/180 mensagens tinham `embeds={}` (object). Mais provável: `embeds: undefined` foi convertido pelo Kysely para `{}` (object literal vazio), e isso passou. Sintoma silencioso: parser nunca achou texto em embed onde havia.
- Reingestões anteriores rodavam contra janelas pequenas (7d) onde os payloads recém-vindos da API Discord coincidiam de não ter embeds não-triviais. Quando rodamos sem janela em 09/05/2026, atingimos posts com embeds não-vazios, e o INSERT quebrou.

Em outras palavras: o bug **sempre existiu**, mas não foi exercido. E166 (evidência fabricada) cobre exatamente isso — declarar GREEN sem rodar contra dados reais em escala.

## Solução

Serializar `embeds` e `attachments` para JSON antes de enviar ao Kysely. Duas alternativas equivalentes:

**Alternativa A (escolhida):** usar `sql<T>` tagged template do Kysely com cast explícito `::jsonb`.

```ts
import { sql } from 'kysely';

attachments: sql<unknown[]>`${JSON.stringify(msg.attachments ?? [])}::jsonb`,
embeds:      sql<unknown[]>`${JSON.stringify(msg.embeds ?? [])}::jsonb`,
```

Funciona em INSERT e UPDATE. Tipo `unknown[]` mantém compatibilidade com `DiscordImportMessagesTable.embeds: Generated<unknown[]>`.

**Alternativa B:** alterar `InsertRow` local para aceitar `string` em `attachments`/`embeds` e fazer `JSON.stringify` direto. Funciona, mas perde a typing do schema.

### Arquivos afetados pela correção

- `backend/src/discord/ingestMessages.ts` — `persistMessages`, ramos INSERT (linhas ~243–250) e UPDATE (linhas ~260–273).

### Não afetado

- `backend/src/routes/adminDiscordSync.ts`: `parsed_payload`, `normalized_payload` são objetos (não arrays). pg auto-stringify funciona; permanece como está.

## Lição aprendida (referência cruzada com E166)

Este bug confirma a regra E166: alegação de GREEN em pipeline de import exige `SELECT` no banco-alvo após o write, não execução de parser/script em memória.

A função `persistMessages` rodou em produção por **5 dias** com este bug latente. As sessões 26-05-04_1 e 26-05-06 declararam GREEN para feature 015 sem nunca terem exercido a serialização sobre payload com embeds não-triviais. A lição:

- Tests unitários do parser **não substituem** integration test do persistMessages.
- "Build verde" e "deploy verde" não dizem nada sobre se o INSERT funciona com payload real.
- Toda feature de pipeline ETL precisa de **smoke test em deploy** que escreva e verifique no banco-alvo. Adicionar como tarefa em Fase 1 do plan.md (T-F1-09).
